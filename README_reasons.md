# 原因分析：长时间未使用导致无法唤醒

经过对代码的分析，应用在长时间后台运行后出现“无法唤醒”的主要原因有两个：

### 1. macOS 的 App Nap (应用休眠) 机制导致主线程挂起 (核心原因)
我们的应用在 `build.sh` 中配置了 `LSUIElement`，使其成为一个无程序坞图标的纯后台/菜单栏应用。当搜索窗口被隐藏且长时间无交互时，macOS 的电源管理策略会极其激进地将该应用置于 **App Nap**（休眠）状态。
- 我们的全局快捷键 (HotKey) 是通过底层 Carbon API 的 `InstallEventHandler` 注册的，它**高度依赖主线程的 RunLoop** 来接收键盘事件。
- 一旦进入 App Nap，主线程的 RunLoop 会被操作系统挂起或严重限流（Throttled）。此时按下全局快捷键，事件将无法被及时派发，导致按键无响应、搜索框无法唤醒。

### 2. 潜在的内存泄漏导致系统 Swap 换页卡顿 (次要原因)
在 Rust 核心引擎 `indexer.rs` 的 `apply_updates()` 方法中，处理文件的新增、修改和重命名事件时，会向 `StringPool` 中追加新的文件名 (`pool.add`)。
- 目前的 `StringPool` 是一个为了极致性能设计的连续内存数组，但**缺乏垃圾回收 (GC) 机制**。被删除或旧版本文件的字符串所占用的内存从未被释放。
- 长时间挂机（尤其是在 OneDrive/TimeMachine 频繁写入的情况下），`StringPool` 的体积会不断膨胀。macOS 最终会将这些不活跃的庞大内存置换到硬盘 (Swap) 中。
- 当你经过一晚上后突然按下快捷键时，系统需要从硬盘将这部分内存重新加载到物理内存，会引发几十秒的巨大延迟（甚至卡死），在体感上表现为“无法唤醒”。
